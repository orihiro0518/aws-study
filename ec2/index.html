Amazon EC2とは？

EC2はAWS上で借りる仮想サーバーです。この記事では「EC2って結局何？」から、AMI・EBS・Security Group・Auto Scaling・料金体系・Dedicated Hostsまで一気につなげて理解します。

この記事の目次EC2とは構成要素周辺サービス料金体系Dedicated HostsLambdaとの違い試験対策

EC2は「AWS上に借りるパソコン」

Amazon Elastic Compute Cloud（EC2）は、AWS上で仮想サーバーを起動できるサービスです。物理サーバーを購入する代わりに、必要なときに必要な性能のサーバーを用意できます。

AWS物理設備を管理
EC2仮想サーバー
OS / ミドルウェア自分で設定できる
アプリWeb・業務処理など

まずこれだけ： EC2＝「サーバーそのものを借りて自由に使う」。自由度が高い代わりに、ゲストOSやアプリケーションの管理は利用者側に残ります。

EC2を作るときに決めるもの

EC2は単体で覚えるより、「EC2の周りに何が付くか」を理解すると一気に整理できます。

項目何を決める？イメージ
AMIOSや初期構成サーバーのテンプレート
インスタンスタイプCPU・メモリなどPCのスペック
EBSディスクSSD/HDDに近い保存領域
VPC / Subnetどのネットワークに置くか社内LAN・セグメント
Security Groupどの通信を許可するか仮想ファイアウォール
IAM RoleEC2からAWSサービスへ何を許可するかEC2に渡す権限

AMI：EC2のひな型

AMI（Amazon Machine Image）はEC2を起動するためのテンプレートです。Amazon Linux、Ubuntu、Windows ServerなどのOSを選んだり、ソフトウェアを入れた独自AMIから同じ構成のEC2を複数作ったりできます。

インスタンスタイプ：CPU・メモリの性能

代表的な系統特徴イメージ
T系バースト可能な汎用小規模・軽めの処理
M系汎用CPUとメモリのバランス
C系コンピューティング最適化CPUを多く使う処理
R系メモリ最適化大量メモリを使う処理
G/P系などアクセラレーテッドコンピューティングGPU利用など

Cloud Practitionerでは細かい型番暗記より、「処理に合わせてCPU・メモリなどの構成を選べる」ことが重要です。

EBS：EC2でよく使うブロックストレージ

EBS（Elastic Block Store）はEC2に接続して使う代表的なブロックストレージです。ざっくりEC2＝PC本体、EBS＝ディスクと考えると分かりやすいです。

注意： EC2とEBSは別物です。「サーバーのディスクが欲しい」ならEBS、「画像やバックアップなどをオブジェクトとして大量保存」ならS3という切り分けが基本です。

Security Group：EC2への通信を制御

Security GroupはEC2などに適用するステートフルな仮想ファイアウォールです。例えばWebサーバーならHTTPS 443を許可し、SSH 22は管理者のIPだけ許可する、といった制御ができます。

EC2はELB・Auto Scalingと組み合わせる

EC2を1台だけ置くより、複数台をELBで振り分け、Auto Scalingで台数を増減する構成がAWSらしい使い方です。

利用者アクセス
ALB / ELB通信を振り分け
EC2 × 複数実際に処理
Auto Scaling台数を自動調整
サービス役割重要ポイント
EC2実際にアプリや処理を動かす仮想サーバー
ELB複数のEC2などへ通信を振り分ける負荷分散
Auto Scaling需要に応じてEC2の台数を増減するEC2の代わりではない

試験用の整理： ELB＝「振り分ける」、Auto Scaling＝「台数を変える」、EC2＝「処理する」。

EC2の料金体系はどう選ぶ？

Cloud Practitionerでは、「何年使うか」「中断されてもいいか」「専有が必要か」という条件から選びます。

料金・購入方式用途こういうときに選ぶメリットデメリット
On-Demand長期契約なしで利用短期・不規則・利用量が読めない柔軟で始めやすい長期の安定利用では割高になりやすい
Savings Plans一定のコンピューティング利用額を1年または3年コミット長期間の利用が見込め、柔軟性も欲しいOn-Demandより割引を受けやすく、RIより柔軟な選択肢になりやすいコミットした利用額の支払いが必要
Reserved Instances特定のインスタンス構成を1年または3年コミット構成・利用が長期間安定しているOn-Demandよりコストを抑えやすい条件が固定されるため柔軟性が下がる
Spot InstancesAWSの未使用EC2キャパシティを利用バッチ、分散処理、再実行できる処理大幅に安くできる可能性AWS側のキャパシティ都合で中断される可能性
Dedicated Hosts物理ホスト単位で専有BYOL、ソケット/コア単位ライセンス、ホスト配置管理が必要物理ホストを可視化・制御しやすい通常構成より高コストになりやすい

覚え方： 普通に使う＝On-Demand ／ 長く使う＝Savings Plans・RI ／ 止まってもいい＝Spot ／ 物理ホストを専有＝Dedicated Hosts。

EC2本体以外にも、EBS、データ転送、Elastic IPなどの利用状況によって別料金が発生する場合があります。

Dedicated Hostsは何が特別？

Dedicated Hostsは、EC2インスタンスを動かす物理サーバーを専有して管理できるオプションです。AWS公式では、ホストID、ソケット数、物理コア数などの可視性や、特定ホストへの配置・ホストアフィニティを提供しています。

通常のEC2物理ホストを意識しない
Dedicated Host物理ホストを専有
EC2を配置配置をより制御
BYOL既存ライセンス活用
Dedicated HostDedicated Instance
他AWSアカウントのインスタンスとの物理分離○○
ホストID・ソケット・コアの可視性○×
特定ホストへの配置・アフィニティ○×
BYOL幅広く対応限定的
課金単位ホスト単位インスタンス単位

試験キーワード： 「既存のソケット単位・コア単位ライセンスを持ち込みたい」「物理ホストを把握・制御したい」→ Dedicated Hostsを疑う。

EC2とLambdaはどう使い分ける？

EC2Lambda
考え方サーバーを借りる処理だけ実行する
OS管理利用者が担当基本的に意識しない
自由度高いEC2より制約あり
向いている処理長時間稼働、OSやミドルウェアを細かく設定イベント駆動、短時間処理、サーバー管理を減らしたい
スケーリングAuto Scalingなどを設計サービス側で自動的にスケール

イメージ： EC2＝「部屋ごと借りる」 ／ Lambda＝「必要な作業だけお願いする」。AWSを使うとき必ずEC2かLambdaを選ぶのではなく、コンピューティングが必要になったときの選択肢として考えます。

EC2を選ぶのはこんなとき

① OSへログインして細かく設定したい
Linux設定、ミドルウェア導入、特殊なランタイムなどを自分で制御したい。
② 長時間・常時稼働するアプリを動かしたい
Web/APサーバーや業務アプリなど、サーバーとして継続稼働させたい。
③ インスタンスのCPU・メモリ構成を選びたい
ワークロードに合わせて汎用、CPU最適化、メモリ最適化などを使い分けたい。
④ 既存アプリを比較的そのまま移行したい
オンプレのサーバー型アプリケーションをAWSへ持っていく場合にも候補になります。

5問ミニチェック

答えを考えてから開いて確認してください。

Q1. OSへログインし、自由にミドルウェアを導入できる仮想サーバーが必要。何を使う？
答え：Amazon EC2
サーバーそのものを借り、OSレベルから管理したい要件に合います。
Q2. アクセス急増に合わせてEC2の台数を自動で増やしたい。何を使う？
答え：EC2 Auto Scaling
ELBは通信を振り分け、Auto Scalingは台数を増減します。
Q3. 中断されても再実行できる大量バッチをできるだけ安く処理したい。何を使う？
答え：Spot Instances
未使用キャパシティを低価格で利用できますが、中断の可能性があります。
Q4. 既存の物理CPUコア単位のソフトウェアライセンスをAWSへ持ち込みたい。候補は？
答え：Dedicated Hosts
物理ホストやソケット・コアを把握でき、BYOL要件で重要です。
Q5. S3への画像アップロード時だけコードを実行したい。EC2より適した候補は？
答え：AWS Lambda
イベント発生時だけ処理を実行し、サーバー管理を減らせます。
